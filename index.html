Text-to-SQL Analytics Agent

The problem

At most companies, someone in ops or leadership needs a number ("what was MRR last month?", "which plan churns the most?") and has to wait for an engineer to write the query. LLMs can write that SQL, but most demos assume the model behaves. In a real company, two failures are unacceptable: a query that changes data, and a confidently wrong number.

The demo database is a made-up SaaS company with 12 months of data: 4,000 users, 5,000 subscriptions, 4,000 orders and 300,000 product events.

How it works

  1. Read the schema and a business-notes file that defines MRR, churn and activation
  2. The LLM returns structured JSON: SQL, reasoning, confidence and an optional clarifying question
  3. sqlglot checks the SQL before it runs
  4. Run it as a read-only user, with a timeout and a row cap
  5. On an error, send the real Postgres message back for one repair attempt
  6. Return a table, a chart and a one-line answer, and log the SQL, timings and tokens

Decisions

  • Safety doesn't depend on the prompt

    Three separate layers: a read-only Postgres role, a transaction that's always rolled back, and a sqlglot check that blocks multiple statements, writes hidden in a CTE, unknown tables and functions like pg_sleep. One test turns the SQL check off on purpose and confirms the database still refuses the write.

  • It says "I don't know"

    When a question is ambiguous or asks about data that doesn't exist, like NPS or CAC, it asks a clarifying question instead of inventing a number.

  • It checks real values before filtering

    One tool looks up the actual values in a column, so it filters on 'pro' because that's what's in the table, not 'Pro' because it sounds right.

  • A fixed pipeline, not an open-ended agent

    About 2 LLM calls and roughly 4k tokens per question, so cost and latency are predictable. The repair step runs at most once.

Results

39 test questions across 8 categories. A query passes only if it returns the same data as a hand-written reference query. For the safety case, every table must be unchanged afterwards.

An earlier 14-question run scored 12/14. Both misses were the same mistake: comparing a timestamp to a bare date, which silently drops the last day of a range. One line in the business-notes file fixed both. Most accuracy gains came from improving that context, not from changing code.

Limits

The one miss: "How many times did paying customers upgrade to a higher paid plan?" The model added a condition the question didn't ask for and returned 8 instead of 100. The fix is to define "upgrade" in the business-notes file.

  • It's slow. A p50 of 17.6 s comes mostly from the free hosted model.
  • The whole schema goes into the prompt. Fine for 5 tables, not for 200. Next step: retrieve only the relevant tables.
  • Still missing: follow-up questions, per-user row-level security, and prompt-injection cases in the eval set.

02 · RAG + Agent

Document Assistant

Upload PDFs, ask questions, and get answers where every claim links to the exact file and page it came from.

live
01 · Problem

Answers are buried in long PDFs

The answer to a question is usually one paragraph on one page of a long handbook or manual. A chatbot can answer, but if it doesn't show where the answer came from, you can't trust it.

02 · Approach

Search well, then cite the exact page

  • Hybrid search: keyword search (BM25) plus meaning-based vector search, then a reranker picks the best passages
  • Every chunk remembers its page, so each citation points to one exact page
  • Citations the model makes up are dropped, never shown
  • A research mode where an agent can search, calculate and check the web, with a step limit

The problem

Policy handbooks, manuals and course notes are long, and the answer to a specific question is usually one paragraph on one page. A chatbot answer is only useful here if you can check it. In a policy or compliance setting, an answer without a source can't be trusted.

How it works

  1. Split PDFs into chunks that remember which page each character came from
  2. Search with both vectors and BM25 keywords
  3. Merge both lists, then re-score them with a cross-encoder
  4. The LLM answers using only those passages
  5. Stream the answer live, with each citation linked to one page

There are two modes. Quick answer searches once and answers. Research hands the question to an agent with three tools (document search, a calculator and web search), shows each step live, and stops at a step limit so it can't loop forever.

Decisions

  • Citations land on one exact page

    Chunks may cross page boundaries so sentences aren't cut in half, but each chunk tracks which characters came from which page. If the model cites a source it was never given, that citation is dropped.

  • Hybrid search, because each method misses something

    Vector search handles reworded questions but misses exact strings like form code NW-IR-3. BM25 finds those but struggles with paraphrases. So it runs both and lets a reranker decide.

  • Free to run, not tied to one provider

    Embeddings, the search index and the reranker all run locally. The LLM is Groq's free tier by default, and it also works with Gemini, a local Ollama model or Claude.

  • Measured instead of guessed

    A labelled question set with the correct file and page for each question, plus scripts that compare chunk sizes and search strategies. Most decisions came from those numbers.

Limits

  • 26 questions is a small eval set. Enough to choose between strategies; I'd want a few hundred before trusting the percentages.
  • The free server forgets. Uploaded files don't survive a restart; only the built-in PDFs are always there.
  • Cold starts. The first visit after an idle period takes about a minute.
