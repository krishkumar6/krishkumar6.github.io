Project 1

Text-to-SQL Analytics

A "chat with your database" service I'd actually be comfortable pointing at a real company's data, with a number for how often it's right.

The problem

At most companies, someone in ops or leadership needs a number ("what was MRR last month?", "which plan churns the most?") and has to wait for an engineer to write the query. LLMs can write that SQL, but most demos quietly assume the model behaves. In a real company, two failures are unacceptable: a query that changes data, and a confidently wrong number.

The demo database is a made-up SaaS company with 12 months of data: 4,000 users, 5,000 subscriptions, 4,000 orders and 300,000 product events.

How it works

  1. Read the schema and a business-notes file defining MRR, churn and activation
  2. LLM returns structured JSON: SQL, reasoning, confidence, clarifying question
  3. sqlglot checks the SQL before it runs
  4. Run as a read-only user, with a timeout and a row cap
  5. On an error, send the real Postgres message back for one repair
  6. Return a table, a chart and a one-line answer
  7. Log the SQL, timings and tokens

Decisions that mattered

  • Safety doesn't depend on the prompt

    Three separate layers: a Postgres role that can only read, a read-only transaction that's always rolled back, and a sqlglot check that rejects multiple statements, writes hidden in a CTE, non-allowlisted tables and functions like pg_sleep. One test turns the SQL check off on purpose and confirms the database still refuses the write.

  • It says "I don't know"

    When a question is ambiguous or asks about data that doesn't exist, like NPS or CAC, it asks a clarifying question instead of inventing a number.

  • It checks real values before filtering

    The model has one tool that looks up the actual values in a column, so it filters on 'pro' because that's what's in the table, not 'Pro' because it sounds right.

  • A fixed pipeline, not an open-ended agent

    About 2 LLM calls and roughly 4k tokens per question, so cost and latency are predictable. The repair step runs at most once.

What improved it

An earlier 14-question run scored 12/14. Both misses were the same mistake: comparing a timestamp to a bare date, which silently drops the last day of a date range. One line added to the business-notes file fixed both. Most of the accuracy gains came from improving that context file, not from changing code.

Where it falls short

The one miss: "How many times did paying customers upgrade from one paid plan to a higher paid plan?" The model added a condition the question didn't ask for. It required a later, higher-tier subscription to exist in the data, so it returned 8 instead of 100. The question is arguably ambiguous, so the fix is to define "upgrade" in the business-notes file.

  • It's slow. A p50 of 17.6 s is mostly the free-tier hosted model. That's fine for a demo but not for a dashboard.
  • The whole schema goes into the prompt. That works for this database, not for one with 200 tables. Next step: retrieve only the relevant tables first.
  • Still missing: follow-up questions ("now split that by plan"), per-user row-level security, and prompt-injection cases in the eval set.

75 tests run against scripted fake LLM responses, so they cost nothing and give the same result every time.

Project 2

Document Assistant

Upload PDFs, ask questions, and get short answers where every claim links to the exact file and page it came from.

The demo runs on a free server that sleeps when idle, so the first visit takes about a minute to wake up.

  • FastAPI
  • Chroma
  • BM25
  • MiniLM reranker
  • Groq
  • Server-Sent Events
  • Docker

The problem

Policy handbooks, manuals and course notes are long, and the answer to a specific question is usually one paragraph on one page. A chatbot answer is only useful here if you can check it. In a policy or compliance setting, an answer without a source can't be trusted at all.

How it works

  1. Split PDFs into chunks that remember which page each character came from
  2. Search with vectors and BM25 keywords
  3. Merge both lists, then re-score with a cross-encoder
  4. LLM answers using only those passages
  5. Stream the answer, with each citation linked to one page

There are two modes. Quick answer searches once and answers. Research hands the question to an agent with three tools (document search, a calculator and web search), shows each step live, and stops at a step limit so it can't loop forever.

Decisions that mattered

  • Citations land on one exact page

    Chunks may cross page boundaries so sentences aren't cut in half, but each chunk tracks which characters came from which page. If the model cites a source it was never given, that citation is dropped instead of shown.

  • Hybrid search, because each method misses something

    Vector search handles reworded questions but misses exact strings like form code NW-IR-3 or 3.85. BM25 finds those but struggles with paraphrases. So it runs both and lets a reranker decide.

  • Free to run, and not tied to one provider

    Embeddings, the search index and the reranker all run locally. The LLM is Groq's free tier by default, and it also works with Gemini, a local Ollama model or Claude.

  • Measured instead of guessed

    The repo has a labelled question set with the correct file and page for each question, plus scripts that compare chunk sizes and search strategies. Most of the decisions here came from those numbers.

The 12-second searches on the free server came from the model runtime starting one busy-waiting thread per visible CPU core, all competing for a tenth of a CPU. Pinning it to a single thread brought searches down to about 3 seconds, and the app runs in around 144 MB of memory.

Where it falls short

  • 26 questions is a small eval set. It was enough to choose between strategies, but I'd want a few hundred before trusting the percentages.
  • The free server forgets. The disk is wiped on every restart, so only the PDFs built into the image are always there. Uploaded files don't survive a restart.
  • Cold starts. The first visit after an idle period takes about a minute.

69 tests cover chunking, citations, retrieval, the agent loop, streaming, caching and security.
